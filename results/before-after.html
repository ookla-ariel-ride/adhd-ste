Before — no ADHD-STE · 734 words

**Most likely story:** enabling pooling introduced two classic `pg.Pool` bugs at once — clients that are never released (or a new pool created per request), which makes the pool/queue grow until OOM, and no `pool.on('error')` handler, so when Postgres or a proxy kills an idle pooled connection you get an unhandled `ECONNRESET` that crashes the process mid-request → 502s. Readiness stays green because your probe doesn't touch the pool. The deploy-overlap 502s are a separate, common issue: no graceful shutdown plus Node's `keepAliveTimeout` being shorter than the load balancer's idle timeout.

## Phase 1 — Evidence first (read-only, zero risk)

1. **Restart reason:** `kubectl describe pod <pod>` → `Last State`. Exit code 137/`OOMKilled` = memory kill; exit code 1/`Error` = crash (points at the unhandled `'error'` event). This one fork decides half the diagnosis.
2. **When do 502s happen?** Pull ingress/LB access logs and bucket 502 timestamps: clustered around rollouts → shutdown/keep-alive problem; steady-state → pool problem. They may be both.
3. **Full ECONNRESET stack traces:** is it the pg client (DB side) or the HTTP server socket (LB side)? Different fixes.
4. **Postgres side:** `SELECT state, count(*) FROM pg_stat_activity GROUP BY state;` sampled over time. Monotonically rising connection count = pool-per-request leak. Also check Postgres/pgbouncer/RDS-proxy logs for "terminating connection" and note any server-side idle timeout.
5. **Read the diff that enabled pooling.** Check specifically: is `new Pool()` a module-level singleton? Is every `pool.connect()` paired with `client.release()` in a `finally`? Is there a `pool.on('error', ...)` handler? What are `max`, `idleTimeoutMillis`, `connectionTimeoutMillis`?
6. **Config audit:** Node `server.keepAliveTimeout` vs LB idle timeout; readiness probe endpoint (does it exercise the pool?); `terminationGracePeriodSeconds`, preStop hook, SIGTERM handler.

**Then one low-risk instrumentation deploy** (rolling, no downtime): log `pool.totalCount / idleCount / waitingCount` plus `process.memoryUsage()` every 30s. A steadily climbing `waitingCount` confirms leaked clients; climbing `totalCount` across restarts of the same pod confirms pool-per-request.

## Likely causes, ranked

1. **Leaked pool clients** — `pool.connect()` without `release()` on error paths. Pool exhausts, requests queue unboundedly (memory ↑), latency spikes, LB times out → 502.
2. **No idle-client error handler** — pg's pool emits `'error'` when a backing connection dies idle; unhandled, it kills the Node process. Matches ECONNRESET + restarts exactly.
3. **Pool created per request** — leaks connections and memory; Postgres hits `max_connections` and starts resetting → ECONNRESET.
4. **`idleTimeoutMillis` longer than a server/proxy/NAT idle timeout** — pool hands out already-dead sockets → ECONNRESET on next query.
5. **Deploy 502s:** old pods get SIGTERM with no graceful drain, and/or `keepAliveTimeout` (Node default 5s) < LB idle timeout (typically 60s), so the LB reuses a socket Node just closed.
6. **Readiness probe too shallow** — a sick pod with an exhausted pool still passes `/healthz`, so it keeps receiving traffic.

## Fixes (all deployable via rolling update, `maxUnavailable: 0`)

```js
// one module-level pool
const pool = new Pool({
  max: 10,                        // pods × max < Postgres max_connections, with headroom
  connectionTimeoutMillis: 5000,  // fail fast instead of queueing forever
  idleTimeoutMillis: 30000,       // below any server/proxy idle kill
});
pool.on('error', (err) => log.warn('idle client error', err)); // stops the crashes

// every checkout:
const client = await pool.connect();
try { /* queries */ } finally { client.release(); }
// or just use pool.query() where you don't need transactions — it auto-releases
```

Graceful shutdown + keep-alive:

```js
server.keepAliveTimeout = 65000;  // > LB idle timeout (e.g. ALB 60s)
server.headersTimeout = 66000;
process.on('SIGTERM', async () => {
  ready = false;                  // readiness probe now fails
  server.close(async () => { await pool.end(); process.exit(0); });
});
```

Deployment spec: add `lifecycle: { preStop: { exec: { command: ["sleep", "10"] } } }` so endpoints propagate before SIGTERM, keep `terminationGracePeriodSeconds` above your slowest request, and make the readiness probe do a `SELECT 1` through the pool with a short timeout.

## Rolling out safely without staging

Ship one change at a time (the error handler + `release()` fix first — it's the root cause candidate), watch for 30–60 min per change. For extra safety, canary: scale a second Deployment with the fixed image and the same service labels to 1 replica, compare its memory curve and 502 rate against the old pods, then promote. `kubectl rollout undo` is your instant rollback. Don't raise the memory limit as a "fix" — it only delays the OOM kill and masks the leak; use it only as a stopgap if you need breathing room while shipping the real fix.

After — with ADHD-STE · 571 words (−22%)

502s plus rising memory after a pooling change almost always means a connection leak or a pool-per-request bug, with keep-alive and shutdown mismatches adding the deploy-time 502s. Diagnose first; every step below is read-only and safe in production.

## Diagnosis plan (about 30 minutes, no risk)

1. Run `kubectl describe pod <pod>` on a restarted pod. Check `lastState.terminated.reason`. `OOMKilled` confirms the memory limit kills it, not the liveness probe.
2. Read the ingress logs at three 502 timestamps. "upstream prematurely closed connection" points at keep-alive or shutdown. "connect() failed" points at a dead pod.
3. Run this on Postgres every 5 minutes, three times: `SELECT state, count(*) FROM pg_stat_activity GROUP BY state;`. A count that only grows means a connection leak.
4. Compare 502 timestamps with `kubectl rollout history` and pod restart times. 502s that cluster around deploys point at shutdown handling, not the pool.
5. Read the pool code. Count how many times `new Pool(...)` runs. Check that every `pool.connect()` has `client.release()` in a `finally` block. Check that `pool.on('error', ...)` exists.

## Most likely causes, ranked

1. **A new `Pool` per request or per handler.** Each pool holds its own connections. Memory climbs, Postgres hits `max_connections` and resets sockets (ECONNRESET), and requests fail with 502. This matches "started after I enabled pooling" best.
2. **Clients not released on error paths.** The pool runs out of clients. New requests queue in memory until the ingress times out with 502.
3. **Idle-timeout mismatch.** Postgres, PgBouncer, or a cloud NAT closes idle connections. The pool then hands out a dead socket. The next query gets ECONNRESET.
4. **Node keep-alive shorter than the ingress.** Node's default `keepAliveTimeout` is 5 seconds. Most ingresses hold sockets for 60. Node closes a socket the ingress still trusts, and the ingress reports 502.
5. **No graceful shutdown.** On SIGTERM the server dies with requests in flight. During the old/new pod overlap, the ingress still routes to the dying pod.

Readiness stays green because the probe does not look at the pool. A pod can have zero free connections and still return 200.

## Fixes (apply one per rolling deploy, in this order)

Each deploys with zero downtime if you set `maxUnavailable: 0` and `maxSurge: 1` in the Deployment strategy. Keep `kubectl rollout undo deployment/<name>` ready. About 2 hours total.

1. Make the pool a single module-level instance. Release every client in `finally`. Add `pool.on('error', () => {})` with logging — without it, one dead idle connection crashes the whole process.
2. Set pool limits: `max` so that `replicas × max` stays under Postgres `max_connections`, `idleTimeoutMillis: 30000` (below the shortest server-side idle timeout), `connectionTimeoutMillis: 5000`.
3. Set `server.keepAliveTimeout = 65000` and `server.headersTimeout = 66000` (above the ingress idle timeout, usually 60s).
4. Add graceful shutdown: on SIGTERM call `server.close()`, then `pool.end()`, then exit. Add a preStop hook (`sleep 10`) and `terminationGracePeriodSeconds: 30` so the ingress drains before the process stops.
5. After the leak is fixed, make readiness honest: fail the probe when `pool.waitingCount` stays above a threshold. Do not make readiness call the database directly — a short DB blip would then take every pod out at once.

Do not raise the memory limit as a fix. It hides the leak and stretches the crash interval.
